# How the Fire compiler works

A walkthrough of the pipeline, in the order a program travels through it. Every
stage is one file and one job, and each hands the next a structure that is
strictly more resolved than the one it received.

```
  source.fire
      │
      ▼
  ┌─────────┐   tokens     ┌────────┐    AST     ┌──────────┐  typed AST
  │  Lexer  │ ───────────► │ Parser │ ─────────► │ Analyzer │ ─────────────┐
  └─────────┘              └────────┘            └──────────┘              │
   lexer.cpp                parser.cpp             sema.cpp                │
                                                                          │
                    ┌─────────────────────────────────────────────────────┤
                    │                                                     │
                    ▼                                                     ▼
             ┌─────────────┐   bytecode   ┌──────┐              ┌──────────────────┐
             │  CodeGen    │ ───────────► │  VM  │              │  x86-64 backend  │
             └─────────────┘              └──────┘              └──────────────────┘
              codegen.cpp                  vm.cpp                backend_x86_64.cpp
                                              │                          │
                                              ▼                          ▼
                                          program output          nasm ─► ld ─► a.out
```

Errors from every stage land in one `DiagnosticEngine`, which is what makes it
possible to report a lexical error and a type error from the same run.

## 1. Source and spans — `source.cpp`

A `SourceFile` owns the text and a precomputed index of line starts. Everything
downstream refers to locations as a `Span`: two 32-bit byte offsets. Spans are
cheap to copy and to store on every AST node, and the cost of turning one into
"line 12, column 5" is paid only when a diagnostic is actually rendered.

`Span::merge` gives a compound expression the extent of its outermost children,
which is what makes a caret run underline `1 + "two"` rather than just the `+`.

## 2. Diagnostics — `diagnostics.cpp`

No pass aborts on its first problem. Each reports into the engine and continues
where it sensibly can, so one run tells you everything wrong with the file.

Three mechanisms keep that from becoming noise:

- **Panic-mode recovery** in the parser: a syntax error abandons the current
  statement and resumes at the next `;` or statement keyword, so one missing
  semicolon reports once.
- **A poison type** in the analyzer: an expression whose type could not be
  determined takes `TypeKind::Error`, and every operator accepts it silently.
  One mistake yields one diagnostic.
- **A hard cap** of 25 errors, so a binary file handed to the compiler by
  accident does not fill the terminal.

## 3. Lexing — `lexer.cpp`

A hand-written scanner over the raw bytes. Unknown input is reported, skipped,
and scanning continues, so the parser still receives a complete token stream.

The two parts worth knowing about: block comments nest, and a `.` starts a
fractional part only when a digit follows it — which is what lets `0..10` lex
as three tokens instead of failing.

Tokens carry decoded payloads. Escape sequences are already resolved and
numbers already converted, so no later pass ever re-reads source text.

## 4. Parsing — `parser.cpp`

Recursive descent, one function per precedence level, listed loosest to
tightest so the grammar reads top to bottom. The eight arithmetic and bitwise
levels share a shape and are generated by a local macro; everything else is
spelled out.

The parser is purely syntactic with two deliberate exceptions:

- `elif` is desugared here into nested if/else, so no later pass knows it
  exists.
- Type annotations are resolved to interned `Type*` immediately. Fire has no
  user-defined types, so `int` and `[str]` are as syntactic as `(` is.

## 5. Semantic analysis — `sema.cpp`

The pass that makes the tree unambiguous. Afterwards:

- every expression has a `Type*`
- every name knows whether it is a local or a global, and which slot
- every call knows whether it reaches a user function or a builtin, and its index
- every function knows its frame size

**Scopes and slots.** A scope stack holds the variables in flight. Scope 0 is
the global scope; declarations there become globals, and everything deeper
becomes a local of the enclosing function. Slots are allocated from a cursor
that is *restored* when a scope closes, with a high-water mark tracking the
maximum. A function with ten sequential blocks therefore has a frame the size
of its deepest block, not the sum of all ten.

**Function collection precedes body analysis**, which is why declaration order
does not matter and mutual recursion needs no ceremony.

**Bidirectional hints.** `analyze_expression` takes an optional expected type,
used only where a literal is genuinely ambiguous — the empty array. It is never
used to coerce.

**Flow analysis.** `always_diverges` decides whether control can fall off the
end of a statement. It understands `return`, both branches of an `if`, calls to
`exit` and `panic`, and `while true` without a `break`. It backs both the
"not every path returns" error and the unreachable-code warning.

## 6. Bytecode generation — `codegen.cpp`

One walk, no intermediate representation. Fire's semantics map onto the
instruction set closely enough that an IR would be a translation step buying an
optimisation the language does not need.

Codegen reports no diagnostics at all. Everything it needs was decided by sema,
so it cannot fail on well-formed input; the invariants are asserted rather than
checked, and reaching one is a compiler bug rather than a user error.

The invariant that shapes the whole design: **every expression leaves exactly
one value on the stack**, `void` calls included, which push a zero. An
expression statement is therefore always exactly one `POP`.

`break` and `continue` are both collected as patch lists. `for` continues at
its increment, which is emitted after the body, so neither target can be
resolved at the jump site.

## 7. The bytecode — `chunk.cpp`

A flat byte vector, a constant pool that interns duplicates, and run-length
source spans so a runtime error can point at an expression.

Two choices worth recording:

- **Absolute jump targets**, not relative displacements. Two extra bytes per
  jump, and an entire class of off-by-one bugs removed from the patching code.
- **Type-specialised arithmetic**: `ADD_I`, `ADD_F` and `CONCAT` are separate
  opcodes. The VM never inspects a tag to decide what `+` means, because the
  checker already did. That is the main runtime dividend of static typing here.

[bytecode.md](bytecode.md) is the full instruction reference.

## 8. The virtual machine — `vm.cpp`

A stack machine. One value stack holds both locals and temporaries; a frame's
base is the index of its slot 0, arguments arrive already in slots `0..arity-1`,
and the stack is resized to `base + local_count` on entry.

What it still checks is what types cannot prove: division by zero, `INT64_MIN /
-1`, shift counts outside 0–63, index bounds on arrays and strings, and call
depth. Each failure carries a message and a help line, and is rendered through
the same diagnostic engine the compiler uses — with a caret on the source
expression and a stack backtrace.

A `std::bad_variant_access` anywhere in the loop is caught and reported as an
internal compiler error. It can only mean codegen emitted an opcode for the
wrong type, and that should never be blamed on the program.

## 9. The native backend — `backend_x86_64.cpp`

Freestanding NASM-syntax assembly for Linux: no libc, entry point `_start`,
and only the `write` and `exit_group` syscalls, with six hand-written helpers
for printing.

It mirrors the bytecode deliberately — a stack machine on the machine stack,
values in `rax`, locals at `rbp-8(n+1)`, arguments pushed right to left so
argument 0 lands at `rbp+16`. It is unoptimised on purpose: the value is that
the lowering is legible next to the bytecode it parallels.

It covers `int` and `bool` throughout, `str` as literals passed to
`print`/`println`, every operator, all control flow, and functions including
recursion. `float`, arrays, dynamic strings and most builtins each need runtime
support the VM already provides properly, so rather than half-implementing them
the backend reports a diagnostic naming the feature and pointing at `fire run`.

The end-to-end suite compiles `tests/native/*.fire` both ways and diffs the
results, which is what stops the two backends drifting apart.

## 10. The builtin library — `natives.cpp`, `natives_runtime.cpp`

Deliberately split in two.

`natives.cpp` holds the *signatures*, one C++ checker function per builtin.
That is what lets `len` accept a `str` or any `[T]`, `pop` return the element
type of whatever array it was handed, and `slice` return its own first
argument's type — generic behaviour Fire's surface syntax cannot express, for
which introducing type variables into the language would have been the wrong
trade.

`natives_runtime.cpp` holds the implementations. They do not re-validate
argument types, because the checkers proved them; they check only what static
typing cannot.

Both halves are keyed by `NativeId`, and the table asserts against
`NativeId::Count`, so a builtin cannot be added to one half and forgotten in
the other.

## Where to start reading

| If you want to…                         | Read                                    |
| --------------------------------------- | --------------------------------------- |
| add a keyword or operator               | `token.hpp`, `lexer.cpp`, `parser.cpp`  |
| add a statement or expression form      | `ast.hpp`, then follow the compile errors |
| change a typing rule                    | `sema.cpp`                              |
| add an opcode                           | `chunk.hpp`, `codegen.cpp`, `vm.cpp`    |
| add a builtin                           | `natives.hpp`, `natives.cpp`, `natives_runtime.cpp` |
| work on native code generation          | `backend_x86_64.cpp`                    |

Adding an AST node produces a compile error in every switch that must handle it,
which is the intended way to find them all.
